# RPM Packaging Conventions

Every spec in `packages/spec-files/` follows the same conventions. The
verify harness in `configs/tests/verify.sh` enforces the runtime contracts;
these are the **source-level** contracts.

## Macro conventions

Add to `~/.rpmmacros`:

```rpmacros
%_topdir /home/jewboy420/linux-synthex/build/rpmbuild
%_tmppath /home/jewboy420/linux-synthex/build/rpmbuild/tmp
%_sourcedir /home/jewboy420/linux-synthex/build/rpmbuild/SOURCES
%_rpmdir /home/jewboy420/linux-synthex/build/rpmbuild/RPMS
%_builddir %{_topdir}/BUILD
%_unitdir /usr/lib/systemd/system
%_userunitdir /usr/lib/systemd/user
%_udevrulesdir /usr/lib/udev/rules.d
%_sysconfdir /etc
%_datadir /usr/share
%_bindir /usr/bin
%_sbindir /usr/sbin
%_libexecdir /usr/libexec
%_libdir /usr/lib
%__meson meson
%meson_build %__meson %{?_smp_mflags}
%meson_install %__meson install -C build --destdir %{buildroot}
%py3_build %{__python3} setup.py build
%py3_install %{__python3} setup.py install --root=%{buildroot}
```

These exist because **Ubuntu’s `rpm` is Fedora-incomplete** — it lacks
Fedora systemd/udev macros and meson/python3 build macros. Without them,
every spec that references `%{_unitdir}` or `%meson` fails with "macro
%{_unitdir} not defined" or "fg: no job control".

## Source0 pattern

Almost every spec references the SynthOS repo tarball:

```spec
Source0:        synthex-repo-%{version}.tar.gz
```

The tarball is generated by `build/scripts/make-srctars.sh 2026.10` and
written to `build/rpmbuild/SOURCES/`. Versions that exist:
`0.1.0, 1.0.0, 2.0.0, 2026.1, 2026.10, 2026.10.0`. Some specs use a
specific version (`%{safety_version}`, `%{theme_version}`, etc.).

## %prep pattern

```spec
%prep
%setup -q -n synthex-repo-%{version}
```

This extracts the tarball to `BUILD/synthex-repo-<version>/` and `cd`s
into it for `%build` and `%install`. Common bugs to avoid:

- `%setup -c -T` — creates an empty dir, doesn’t extract.
- Forgetting `-n synthex-repo-%{version}` — rpm uses `%{name}-%{version}`
  which gives a different dir name (e.g. `synthex-control-center-2.0.0/`)
  and install paths break.

## %build pattern

For Python/QML/data packages:

```spec
%build
true
```

For compiled Rust daemons (e.g. `synthex-stored`):

```spec
%build
mkdir -p target/release
install -m755 /home/jewboy420/linux-synthex/target/release/%{name} \
    target/release/%{name}
```

(We don’t actually compile inside rpmbuild — the binaries are prebuilt in
the project’s `target/release/` and we just copy them in. This is what
makes the host-side build fast.)

For compiled Cargo daemons that *don’t* ship a prebuilt binary (e.g.
`synthex-control-center`), the spec is currently broken — it references
a binary that isn’t built here. These are intentionally left to fail in
the host build; they belong in the Fedora builder container.

## %install pattern

Two flavors:

**Pure-data / config:**

```spec
%install
install -d %{buildroot}%{_datadir}/synthex/foo
cp -r src/synthex-foo/. %{buildroot}%{_datadir}/synthex/foo/
```

**Python with a launcher:**

```spec
%install
install -d %{buildroot}%{_libexecdir}/synthex/foo %{buildroot}%{_bindir}
cat > %{buildroot}%{_bindir}/synthex-foo <<'LAUNCH'
#!/usr/bin/env bash
exec python3 %{_libexecdir}/synthex/foo/main.py "$@"
LAUNCH
chmod 0755 %{buildroot}%{_bindir}/synthex-foo
cp -r src/synthex-foo/. %{buildroot}%{_libexecdir}/synthex/foo/ 2>/dev/null || true
```

## %files pattern

Mirror what `%install` actually produces. Common bug: `%files` lists
files that `%install` never created → "File not found" at packaging time.
Fix: keep `%files` minimal and matching.

```spec
%files
%{_bindir}/synthex-foo
%{_libexecdir}/synthex/foo/
%config(noreplace) %{_sysconfdir}/synthex/foo.conf
```

## %post / %postun

Use only Fedora macros; don’t write shell with `set -e` that could mask
failures. Minimal example:

```spec
%post
systemctl daemon-reload 2>/dev/null || true
systemctl try-restart synthex-foo.service 2>/dev/null || true

%postun
systemctl daemon-reload 2>/dev/null || true
```

## The synthex-aios spec (the umbrella)

`packages/spec-files/synthex-aios.spec` is the spec we authored in-tree.
It bundles the entire AI-OS layer (`configs/aios/`, `configs/upstream/`,
`configs/performance/`) into a single noarch RPM:

```
/usr/bin/synthex
/usr/bin/synthex-game-session
/usr/sbin/synthex-doctor
/usr/sbin/synthex-persona
/usr/sbin/synthex-install
/usr/sbin/synthex-update-sync
/usr/sbin/synthex-defaults
/usr/lib/systemd/system/synthex-defaults.service
/usr/lib/systemd/system/synthex-zram.service
/usr/lib/systemd/system/synthex-sync-updates.{service,timer}
/usr/share/synthex/aios/post-install.sh
/usr/share/synthex/performance/zram-setup
/etc/sysctl.d/00-synthex-vm.conf
/etc/sysctl.d/00-synthex-network.conf
/etc/gamemode.ini
/etc/snapper/configs/root
/etc/synthex/upstream/synth-pkgs.conf
```

Requires: `synthex-brain`, `synthex-hermes` (the AI daemons).

## Verification

`configs/tests/verify.sh` validates that the spec’s output behaves
correctly at runtime. See `docs/README.md#at-a-glance`.

## Adding a new spec

1. Write the `.spec` to `packages/spec-files/`.
2. Copy it to `build/rpmbuild/SPECS/`.
3. If it references new repo content, add the files to the appropriate
   dir (`src/`, `systemd/`, `services/`, etc.), then regenerate tarballs:
   ```bash
   build/scripts/make-srctars.sh 2026.10
   ```
4. If it references new top-level sources (not in the tarball), put them in
   `build/rpmbuild/SOURCES/` and declare them in the spec as `Source1:` etc.
5. Build it:
   ```bash
   /home/jewboy420/build_batch.sh <yourspec>.spec
   ```
6. Add it to the local repo:
   ```bash
   cp build/rpmbuild/RPMS/noarch/<yourspec>.rpm build/repo/noarch/
   cd build/repo/noarch && createrepo_c .
   ```
7. Run the verify harness:
   ```bash
   configs/tests/verify.sh; echo $?
   ```
8. If the harness needs to know about the new spec, extend it.
